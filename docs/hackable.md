# Hackable mode

```sh
dotnet fsi setup.fsx --hackable                 # default mode + Fable from source + self-check + hot-patch test
dotnet fsi setup.fsx --hackable --no-hotpatch   # same, without the SageFs hot-patch test
dotnet fsi setup.fsx --check --hackable         # self-checks and hot-patch test only
dotnet fsi tests/hotpatch/HotPatch.fsx          # hot-patch test only
```

Default mode gives you Fable's compiler as the NuGet package (optimized). You can call it, but you
cannot change it. Hackable mode builds Fable's compiler assemblies from source, unoptimized, and loads them into a
SageFs session. You can then redefine a function inside Fable from the REPL and see the result on the next compile,
without a rebuild.

## What it produces

All of it is gitignored and regenerated by `setup.fsx --hackable`. Reruns are idempotent.

| Path | What |
|------|------|
| `.work/fable/` | Shallow clone of Fable at the exact commit the pinned `Fable.Compiler` package was built from (from the package's `.nuspec`). |
| `hackable/Directory.Build.props` | `Optimize=false`, the pinned fsc (below), and the renamed FCS fork from `vendor/`. |
| `hackable/fable/<Project>/` | `Fable.AST`, `Fable.Transforms`, `Fable.Transforms.Babel` and `Fable.Compiler`. These use upstream's assembly names and source lists, with sources linked from `.work/fable/src`. |
| `hackable/Fable.SageFs.Hackable.fsproj` + `Playground.fs` | The SageFs session project. `Playground.fs` is copied from `templates/session/`. |
| `hackable/Fable.SageFs.Hackable.props` | The references, imported by the session project and by `tests/smoke` (`-p:FableSageFsMode=hackable`). |

### Why unoptimized

SageFs hot reload works by detouring methods. In an optimized build, fsc inlines across modules, so about 18% of
the methods in `Fable.Transforms` have no call site left to detour.

### Why a pinned fsc

`versions.json` `debugSdk` pins the SDK (10.0.112). With SDK 10.0.4xx, fsc emits invalid Debug IL for Fable
(`Fable2Babel.Util.transformCurriedApply` throws `InvalidProgramException`). The pinned fsc is set through
`DotnetFscCompilerPath`, so any build of these projects uses it, including a SageFs
`hard_reset_fsi_session rebuild=true`. If this SDK is missing, setup stops and says what to install.

## Using it

Open a SageFs session on `hackable/Fable.SageFs.Hackable.fsproj` with working directory `hackable/`:

```fsharp
Playground.fableReport ();;      // four assemblies, all "unoptimized", FCS: Fable.FSharp.Compiler.Service
Playground.selfCheck () |> Playground.printChecks;;
let jsA = Playground.compileHello ();;
```

### Hot-patching a Fable function (verified)

Redefine the function with `send_fsharp_code`. Follow these rules:

- Mirror its full module path with nested modules. SageFs rejects `namespace` in evals.
- Qualify Fable types with `global.`, because the nested `module Fable` shadows the `Fable` namespace.

```fsharp
module Fable =
    module Transforms =
        module Fable2Babel =
            module Util =
                let getUnionCaseName (uci: global.Fable.AST.Fable.UnionCase) =
                    "HOTPATCH:" + (match uci.CompiledName with
                                   | Some cname -> cname
                                   | None -> uci.Name);;
Playground.compileHello ();;     // return ["HOTPATCH:Circle", "HOTPATCH:Rect"];
```

To undo the patch, send the original body again. The next compile then matches `jsA` exactly.
`tests/hotpatch/HotPatch.fsx` runs this whole sequence against a session it creates. Measured on the author's
machine with SageFs 0.6.830:

- The patch eval took 270 ms.
- The recompile took 10 ms.
- Edit to JS, including the MCP round-trips, took about 360 ms.
- The first patch in a long-running session was slower: about 10 s once.

### Editing Fable's source files

Fable's sources live in `.work/fable/src`. The generated projects link them, so edit them there.

- SageFs's file watcher does not apply these edits. It watches only the session's working directory
  (`hackable/`), and `.work/fable/src` is outside it. For a quick change, send the edited definition as an eval, as
  above. To pass a file path, call `send_fsharp_code` with `file_path` and `eval_mode=block`.
- To load the edited files into the session, run `hard_reset_fsi_session` with `rebuild=true`. This rebuilds with
  the pinned fsc. This path has not been timed yet.
- `git -C .work/fable diff` shows your changes, and `git -C .work/fable checkout -- .` reverts them. Setup keeps
  your edits and warns about them. It stops only if the pinned commit changed while the clone is dirty.

## The hot-patch test

`tests/hotpatch/HotPatch.fsx` talks to the running SageFs daemon over its MCP HTTP endpoint. It reads the port from
`~/.SageFs/daemon-info.json`. It never starts, stops or restarts the daemon, and it only touches the session it
creates. It always stops that session.

1. Creates a session on `hackable/Fable.SageFs.Hackable.fsproj` and waits until Ready.
2. Checks that the four Fable assemblies are unoptimized and bound to the renamed FCS fork.
3. Compiles `samples/Hello`. The output must equal `Hello.expected.js` (`.work/hotpatch/A.js`).
4. Patches `Fable2Babel.Util.getUnionCaseName`. The JS must change on exactly one line, the union case names
   (`B.js`).
5. Sends the original body again. The JS must equal `A.js` (`A2.js`).

Exit codes:

- 0: passed.
- 1: failed.
- 3: skipped. Either no reachable daemon, or another session already uses `hackable/`. The test prints the manual
  steps instead. `setup.fsx` shows a skip as a warning, not a failure.
